## 你要做的事（一句話版）

把傳家知保的登入改成 Google OAuth，建立顧問名單管理，再讓系統每天自動分配 20 份保單給每位顧問，並透過 Gmail 發送每日通知與提醒。

## 背景和動機

目前系統用固定帳號密碼登入，無法支援多位顧問各自登入審核。要讓 20+ 位顧問各自登入、各自看到自己被分配的保單，需要：
1. Google OAuth 讓每個顧問用 Google 帳號登入
2. 管理者預先建立允許登入的顧問名單
3. 每日自動分配 20 份保單 + Email 通知

# Phase 1：Google OAuth 登入 + 顧問管理

## 具體步驟

### Step 1：Google Cloud Console 設定（你需要做）

- 做什麼：到 Google Cloud Console 建立 OAuth 2.0 憑證
- 步驟：
  1. 前往 https://console.cloud.google.com → 建立新專案或選現有專案
  2. 左側「API 和服務」→「憑證」→「建立憑證」→「OAuth 2.0 用戶端 ID」
  3. 應用程式類型選「網頁應用程式」
  4. 授權重新導向 URI 填入：`http://localhost:3000/api/auth/google/callback`（開發用）
  5. 建立後取得 **Client ID** 和 **Client Secret**
- 產出：你拿到 `GOOGLE_CLIENT_ID` 和 `GOOGLE_CLIENT_SECRET` 兩組值，填入 `.env`
- 注意：日後要部署到正式環境，需要再加一個正式網址的 redirect URI

### Step 2：DB Schema — 新增 advisors table

- 做什麼：在 `lib/db.ts` 的 schema 初始化中新增 `advisors` 和 `auth_sessions` 兩個資料表
- 欄位設計：
  ```sql
  -- 顧問名單（管理者預先建立）
  advisors (
    id TEXT PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,  -- Google 帳號 email
    name TEXT NOT NULL,
    is_admin INTEGER DEFAULT 0,  -- 1 = 管理者帳號
    is_active INTEGER DEFAULT 1, -- 0 = 停用
    created_at TEXT DEFAULT (datetime('now'))
  )

  -- 登入 session
  auth_sessions (
    token TEXT PRIMARY KEY,
    advisor_id TEXT NOT NULL,
    expires_at TEXT NOT NULL
  )
  ```
- 產出：`data/policies.db` 多兩張 table，現有資料不受影響
- 注意：第一個管理者帳號要手動 INSERT 到 advisors（或在 seed 腳本裡預設）

### Step 3：建立 Google OAuth API 端點

- 做什麼：在 `app/api/auth/` 新增兩個 route
  - `GET /api/auth/google` — 產生 Google 授權 URL 並 redirect
  - `GET /api/auth/google/callback` — 接收 Google 回傳的 `code`，換取 access token，取得用戶 email，驗證是否在 advisors 名單內，建立 session cookie
- OAuth 流程：
  1. 用戶點「Google 登入」→ 導向 `https://accounts.google.com/o/oauth2/v2/auth?...`
  2. 用戶同意授權 → Google redirect 回 `/api/auth/google/callback?code=XXX`
  3. server 用 code 換取 `id_token` → 從 token 解析 email
  4. 查 advisors table，email 在名單內 → 建立 session token，寫入 `auth_sessions`
  5. 設定 `HttpOnly` cookie，redirect 到 `/`
- 產出：可以正常完成 Google 登入流程的 API
- 注意：state 參數需要做 CSRF 防護（用 `crypto.randomUUID()` 產生，存在 cookie 裡驗證）

### Step 4：更新 auth middleware (proxy.ts)

- 做什麼：修改 `proxy.ts`，從驗證固定帳密改成驗證 session token
- 邏輯：讀取 cookie 中的 session token → 查 `auth_sessions` table → 驗證未過期 → 放行
- 保留：`/api/auth/google` 和 `/api/auth/google/callback` 這兩個路徑不需要驗證（白名單）
- 管理者識別：session 裡帶 `is_admin` flag，用於後台頁面的進入控制
- 產出：原有登入保護正常運作，但用 Google session 取代固定帳密
- 注意：`lib/db.ts` 要 export 一個 `getAdvisorBySessionToken()` 的 helper function

### Step 5：管理者後台 — 顧問名單頁面

- 做什麼：新增 `app/(dashboard)/admin/advisors/page.tsx`
- 功能：
  - 列出所有顧問（email、姓名、狀態、建立時間）
  - 新增顧問（填 email + 姓名）
  - 停用/啟用顧問（切換 is_active）
  - 設定/取消管理者（切換 is_admin）
- API 端點：`/api/admin/advisors` — GET（列表）、POST（新增）、PATCH（更新）
- 進入限制：只有 `is_admin = 1` 的帳號才能進此頁面
- 產出：管理者登入後可在後台管理顧問名單

### Step 6：登入頁面改版

- 做什麼：修改 `app/login/page.tsx`
- 改法：移除帳號密碼 form，換成「使用 Google 帳號登入」按鈕
- 點擊行為：`window.location.href = '/api/auth/google'`
- 錯誤狀態：若 Google 登入成功但 email 不在名單內，顯示「您的帳號尚未開通，請聯繫管理員」
- 產出：乾淨的 Google 登入頁面

## 可能遇到的風險

- **Google Cloud Console 設定問題**：redirect URI 要完全一致（含 http/https、斜線），一個字不對就會 401。Step 1 完成後先測試本地登入流程再繼續。
- **現有帳密 admin 帳號消失**：改完後原有的 `SITE_USERNAME/SITE_PASSWORD` 失效。需要在 advisors table 預先 INSERT 管理者的 Google email，否則改完沒有任何人能進去。
- **Safari 對 HttpOnly cookie 的處理**：本地 localhost 開發時部分瀏覽器行為不同，建議優先用 Chrome 測試。

# Phase 2：每日保單分配 + Gmail Email 通知（之後規劃）

> 這個階段在 Phase 1 完成、顧問可以正常登入後再執行。

## 大方向

### Step 7：DB Schema — 分配紀錄

```sql
policy_assignments (
  id TEXT PRIMARY KEY,
  product_id TEXT NOT NULL,    -- 對應 products table
  advisor_id TEXT NOT NULL,    -- 對應 advisors table
  assigned_date TEXT NOT NULL, -- 格式：YYYY-MM-DD
  status TEXT DEFAULT 'pending', -- pending / completed / skipped
  completed_at TEXT
)
```

### Step 8：每日分配 API（早上 8:00 觸發）

- 取出待審核保單 → 平均分配給 active 顧問（每人 20 份）→ 寫入 `policy_assignments`
- Trigger 方式：Zeabur 的 Cron 觸發 `POST /api/cron/assign-daily`（帶固定 secret header 驗證）

### Step 9：Gmail SMTP Email 通知（nodemailer）

- 早上 8 AM：每位顧問收到「今日待審核清單」（20 份保單的名稱 + 連結）
- 晚上 9 PM：查詢尚未完成審核的顧問 → 發提醒 email
- SMTP 設定：Gmail 需要開啟「應用程式密碼」（2FA 後才能設定）

### Step 10：審核頁面加入分配視角

- 顧問登入後，審核頁顯示「今日我負責的 20 份」而非所有待審核保單
- 管理者可以看到所有人的進度
