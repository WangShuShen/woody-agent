## 一、產品定位與目標用戶

### 產品定義
傳家知保是一套**保險業務員用的 AI 保單分析工具**，核心價值：
- 業務員上傳客戶保單 PDF → AI 自動解析保障結構 → 輸出「全險圖」
- 全險圖用來發現客戶的保障缺口，作為加保建議的依據

### 目標用戶
| 角色 | 使用情境 |
|------|----------|
| **審核顧問**（主要） | 每天審核 AI 分析結果、修正錯誤欄位、標記驗證通過 |
| **管理員** | 管理顧問帳號、查看每日進度、設定系統 |
| **一般顧問**（輔助） | 查詢商品目錄、查看歷史分析 |

### 目前部署環境
- **前端 + API**：Vercel（Next.js 16 App Router）
- **資料庫**：Turso（SQLite 邊緣資料庫）
- **AI**：Anthropic API（claude-haiku + claude-sonnet）
- **檔案儲存**：Vercel Blob（production）/ 本機 fs（dev）
- **登入**：Google OAuth 2.0（白名單制）

## 三、核心功能詳細說明

### 3.1 保單分析（/analyze）

**觸發方式**：顧問手動上傳保單 PDF 或圖片檔

**輸入**：
- 保單 PDF / 圖片（一次可上傳多張屬同一張保單）
- 投保保額（必填，例：「100萬」）
- 選填：計劃代號、型態（甲型/乙型）、年份、版次

**輸出**：
- 全險圖 JSON（包含所有險種保障金額）
- 儲存到資料庫（products + analyses tables）
- 儲存 PDF 檔案（Vercel Blob 或本機）

**AI 分析流程（兩階段）**：

```
Step 0：Haiku 險種偵測（快速、便宜）
  ↓ 輸入：保單前兩頁
  ↓ 輸出：{ category: "定額醫療", confidence: 92 }
  ↓ 若 confidence < 70 → 跳過，使用通用 prompt

Step 1：Sonnet 完整分析（精準、較貴）
  ↓ 輸入：全部保單頁面 + 保額
  ↓ System Prompt 選擇：
  │   → 有專科 prompt（specialistPrompts.ts）→ 用專科
  │   → 無專科 → 用通用大 system prompt（300+ 行）
  ↓ Prompt Caching：cache_control: ephemeral（降低重複 token 成本）
  ↓ 輸出：全險圖 JSON
```

**快取機制（節省 AI 費用）**：
- 同一份保單（相同 company + planCode + planType + year + version）且投保保額相同 → 直接從 DB 取，不打 API
- 人工校正記錄（corrections table）自動套用到快取結果

**驗證機制（/api/verify）**：
- 顧問可選擇「AI 驗證」：把原始 PDF + 分析 JSON 再丟給 Sonnet
- Sonnet 扮演「稽核員」找出可疑欄位
- 輸出 overallConfidence 分數 + suspiciousFields 列表

---

### 3.2 商品查詢（/catalog）

**資料來源**：
- TII 保發中心爬蟲（`seed-catalog` API）
- 本機 JSON 檔（`data/tii_sanshang_products.json` 等）

**功能**：
- 依保險公司 / 關鍵字 / 險種 / 在售狀態 篩選商品
- 點選商品 → 側拉抽屜 → 顯示：
  - 商品基本資訊（公司、計劃代號、在售/停售、起訖日期）
  - PDF 條款瀏覽（透過 `/api/pdf-proxy` 從 TII 代理）
  - 若已有 AI 分析 → 顯示「查看全險圖」按鈕

**PDF 代理流程**：
```
前端 → /api/pdf-proxy?planCode=XXXXX
     → 後端向 TII insprod.tii.org.tw 請求
     → 串流回傳 PDF bytes
     → 前端用 Blob URL 塞進 <iframe>
```

---

### 3.3 保單審核（/review）

**來源**：每日自動分配（cron job）從 Google Drive 的待審核清單

**審核佇列邏輯**：
```
/api/cron/assign-daily（每日觸發）
  ↓ 掃描 DB_DIR（本機目錄）中的 analyzed/ 資料夾
  ↓ 找出未分配的保單 UUID
  ↓ 用 Round-Robin 分配給活躍顧問
  ↓ 寫入 policy_assignments table
  ↓ 發 Email 通知顧問（sendDailyAssignment）
```

**審核流程**：
```
顧問看佇列 → 點選任務 → /review/[id]
  ↓ 從 DB_DIR 讀取分析 JSON（左欄）
  ↓ 從 Google Drive 讀取原始 PDF（右欄，pdf-proxy/local）
  ↓ 顧問逐欄比對、修改
  ↓ 按「儲存結果」→ /api/review/[id] POST
    → 寫回 analyzed/*.json 檔案
    → 執行 Python 腳本更新 Drive
    → policy_assignments.status = 'completed'
```

**特殊功能**：
- PDF 跳頁：因 react-pdf TextLayer 問題，改用 HTTP 分頁請求（`/api/review/[id]?page=N`）

### 3.4 管理後台

**顧問管理（/admin/advisors）**：
- 查看所有顧問列表（email、名稱、狀態）
- 新增顧問（POST /api/admin/advisors）
- 停用顧問（DELETE /api/admin/advisors?id=xxx）
- 僅限 is_admin = 1 的顧問操作

**今日進度（/admin/progress）**：
- 查看當天各顧問的分配量 vs 完成量
- 來自 policy_assignments table 統計

## 四、資料庫 Schema

### 4.1 資料表關係圖

```
companies (1) ─── (N) products (1) ─── (N) analyses
                       │
                       └── (N) corrections

advisors (1) ─── (N) policy_assignments
```

### 4.2 各資料表說明

**companies**
```sql
id          INTEGER PK
name        TEXT UNIQUE          -- 保險公司名稱
created_at  TEXT
```

**products**（保險商品目錄）
```sql
id                INTEGER PK
company_id        INTEGER FK → companies
product_name      TEXT             -- 商品名稱
plan_code         TEXT             -- 計劃代號（如 QDHL2）
plan_type         TEXT             -- 甲型/乙型/丙型
year              TEXT             -- 條款年份（民國年）
version           TEXT             -- 版次
category          TEXT             -- 定額醫療/醫療實支/壽險/意外險/防癌險/重大傷病/長照/失能
coverage_template TEXT             -- AI 分析 JSON（全險圖結構）
file_path         TEXT             -- 條款 PDF 路徑
verified          INTEGER DEFAULT 0 -- 0=未審核, 1=已審核通過

UNIQUE(company_id, plan_code, plan_type, year, version)
```

**analyses**（保單分析記錄）
```sql
id             INTEGER PK
product_id     INTEGER FK → products
insured_amount TEXT             -- 投保保額（如「100萬」）
analysis_json  TEXT             -- 完整分析 JSON
file_path      TEXT             -- 上傳的原始 PDF 路徑
created_at     TEXT
```

**corrections**（人工校正記錄）
```sql
id          INTEGER PK
product_id  INTEGER FK → products
field_path  TEXT             -- 欄位路徑，如「fixedMedical.hospitalDaily」
old_value   TEXT             -- 原始值
new_value   TEXT             -- 修正後的值
note        TEXT             -- 備註
created_at  TEXT
```

**advisors**（顧問帳號）
```sql
id         TEXT PK              -- Google 用戶 ID
email      TEXT UNIQUE
name       TEXT
is_admin   INTEGER DEFAULT 0
is_active  INTEGER DEFAULT 1
created_at TEXT
```

**policy_assignments**（每日審核分配）
```sql
id            TEXT PK
policy_uuid   TEXT             -- 保單 UUID（對應 Drive 上的檔案）
advisor_id    TEXT FK → advisors
assigned_date TEXT             -- 分配日期（YYYY-MM-DD）
status        TEXT             -- pending / completed
completed_at  TEXT
created_at    TEXT

UNIQUE(policy_uuid, assigned_date)
```

## 六、資料流程圖

### 6.1 保單分析主流程

```
顧問瀏覽器
    │
    ├─ 上傳 PDF + 填寫保額
    ▼
/api/analyze (POST)
    │
    ├─ [Step 0] 呼叫 Haiku API
    │   └─ 偵測險種 → detectedCategory
    │
    ├─ 查詢 DB：同 planCode 是否有快取？
    │   ├─ 有快取 + 保額相同 → applyCorrections → 直接回傳（fromCache=true）
    │   └─ 無快取 → 繼續
    │
    ├─ [Step 1] 呼叫 Sonnet API
    │   ├─ 選擇 system prompt（專科 or 通用）
    │   └─ prompt caching 啟用
    │
    ├─ 解析 JSON 輸出
    │
    ├─ 儲存 PDF 檔案（Vercel Blob or 本機）
    │
    └─ 寫入 DB（products + analyses）
         │
         ▼
    回傳全險圖 JSON 給前端
         │
         ▼
    前端渲染 InsuranceChart / InsuranceFormChart
```

### 6.2 保單審核流程

```
Cron Job（每日）
    │
    ├─ 掃描 DB_DIR/analyzed/*.json
    ├─ 找出無分配的 policy_uuid
    ├─ Round-Robin 分配給活躍顧問
    ├─ INSERT policy_assignments（status=pending）
    └─ 發 Email 通知顧問

顧問登入 → /review
    │
    ├─ GET /api/review → 顧問當天的 pending 任務列表
    │
    ├─ 點選任務 → /review/[id]
    │   ├─ GET /api/review/[id] → 讀取 analyzed/*.json
    │   └─ GET /api/pdf-proxy/local → 讀取原始 PDF
    │
    ├─ 顧問修改欄位
    │
    └─ POST /api/review/[id]
        ├─ 寫回 analyzed/*.json
        ├─ 執行 Python（更新 Drive）
        └─ UPDATE policy_assignments SET status='completed'
```

### 6.3 登入認證流程

```
顧問瀏覽器
    │
    └─ GET /api/auth/google
            │
            └─ redirect → Google OAuth
                    │
                    └─ GET /api/auth/google/callback?code=xxx
                            │
                            ├─ 交換 code → access_token
                            ├─ 取得 userInfo（email, name）
                            ├─ 查 DB：email 在 advisors 白名單？
                            │   ├─ 是 → 簽發 JWT（7天）→ Set-Cookie
                            │   └─ 否 → redirect /login?error=not_authorized
                            └─ redirect /
```

### 6.4 商品查詢 + PDF 瀏覽流程

```
顧問 → /catalog
    │
    ├─ GET /api/products?action=meta → 取得公司/險種清單（下拉選項）
    │
    ├─ 填篩選條件 → GET /api/products?company=X&keyword=Y
    │   └─ searchProducts() 查 DB → 回傳商品列表
    │
    └─ 點選商品 → ProductDrawer
            │
            └─ GET /api/pdf-proxy?planCode=XXXXX
                    │
                    └─ 後端向 TII 發請求
                        ├─ 成功 → 串流 PDF bytes
                        └─ 失敗（需登入）→ 顯示「前往保發中心」連結
```

## 七、現有架構的限制與問題盤點

### 7.1 認證安全性問題

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| **多數 API 無認證保護** | 高 | `/api/analyze`、`/api/history`、`/api/correction`、`/api/pdf-proxy` 等都沒有驗證登入狀態，任何人可呼叫 |
| **Cron API 用簡單 Secret** | 中 | `x-cron-secret` header 驗證，Secret 存在 env，可接受但需確保不外洩 |
| **白名單制但無邀請流程** | 低 | 管理員需手動 API 建帳號，沒有自助申請介面 |

### 7.2 資料架構問題

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| **analyses 與 products 的更新不同步** | 中 | 分析是存在 analyses table，但 review 修改的是 JSON 檔案，兩邊資料可能不一致 |
| **coverage_template 混用兩種來源** | 中 | 有些是 AI 分析結果，有些是 TII catalog 資料（用 `_source: "tii_catalog"` 區分），schema 設計不清晰 |
| **corrections 無版本控制** | 低 | 同一個欄位多次校正只保留最新，無法追溯變更歷史 |
| **policy_assignments 的 policy_uuid 對應的是檔案路徑，不是 DB id** | 中 | 耦合了 DB_DIR 檔案結構，不適合 cloud-native 部署 |

### 7.3 效能問題

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| **PDF 代理沒有快取** | 中 | 每次點開商品都重新向 TII 請求，TII 有時很慢（3-5秒）|
| **快取 key 設計偏嚴** | 低 | 必須完全符合 company+planCode+planType+year+version 才命中快取，稍有差異就重打 AI |
| **DB 查詢無 index** | 低 | products 查詢頻繁，缺少 plan_code、company_id 的複合 index |

### 7.4 使用者體驗問題

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| **保額輸入無單位提示** | 中 | 輸入「100」不知道是 100 元還是 100 萬，影響分析準確性 |
| **分析完無法直接推送到客戶** | 高（業務需求） | 全險圖只能在網站看，無法直接分享給客戶或存成 PDF |
| **多保單合計功能入口不明顯** | 中 | 已有 aggregatePolicies 邏輯，但 UI 上要先到分析頁才能看到合計 |
| **無客戶管理功能** | 高（業務需求） | 沒有「這個全險圖是哪個客戶的」的對應關係 |

### 7.5 AI 分析品質問題

| 問題 | 嚴重度 | 說明 |
|------|--------|------|
| **倍數換算仍有錯誤** | 中 | 加護病房「額外加給型」vs「倍數型」容易混淆，prompt 雖有說明但 Sonnet 仍偶爾出錯 |
| **舊版條款辨識率低** | 低 | 民國 80 年代的條款 OCR 品質差，分析結果較不可靠 |
| **沒有自動重試機制** | 低 | AI 分析失敗只顯示錯誤，不會自動用較寬鬆的 prompt 重試 |

## 八、優化方向建議

### Phase 1：安全性補強（立即）
1. 所有 API route 加上 `requireAuth()` middleware
2. 分析、歷史、校正等 API 要驗 JWT Cookie

### Phase 2：資料架構重整（短期）
1. `analyses` table 加入 `reviewed_json` 欄位，讓 review 結果存回 DB（不依賴本機檔案）
2. `corrections` 改為 append-only，加 `reverted_at` 支援回滾
3. `products` 加複合 index：`(company_id, plan_code, plan_type)`

### Phase 3：UX 強化（中期）
1. 保額輸入依險種自動切換單位（壽險→萬、醫療→元/日）
2. 分析結果可以「複製連結」或「輸出 PDF」分享給客戶
3. 新增客戶管理功能，保單和客戶建立對應關係

### Phase 4：AI 品質提升（中期）
1. 加入 prefill 功能：輸入商品名稱自動帶入已知的 planCode / category
2. 低信心欄位自動標紅提醒顧問重點檢查
3. 建立「已知錯誤商品」黑名單，自動套用修正規則

### Phase 5：商品資料庫補強（長期）
1. Google Drive 雙向同步：把網站分析結果同步回 Drive
2. 從 Drive Sheets 讀取自訂商品資料表（擴充 TII 以外的保單）
3. 商品版本比較：同一商品不同年份的保障差異自動標示
