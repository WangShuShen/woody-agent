# 保單分析頁面改造：支援保戶多張保單一次分析

> 建立時間：2026-06-10
> 類型：改善優化
> 狀態：待執行

---

## 你要做的事（一句話版）

把「保單分析」頁面從「一次分析一張保單」改造成「一次上傳保戶的所有保單、拿到總保障全險圖」。

## 背景和動機

顧問與保戶面談時，需要快速掌握保戶「現有所有保障」的全貌（多家保險公司、多個險種）。目前每次只能分析一張保單，效率低且無法一眼看到整體保障缺口。

## 行為變更說明

| | 改造前 | 改造後 |
|:--|:--|:--|
| 上傳多個檔案 | 視為同一張保單的多頁 | 每個檔案 = 一張獨立保單 |
| 保額欄位 | 一組（全域） | 每張保單各自設定 |
| 分析結果 | 單張全險圖 | 合併總表 + 個別保單明細 |

> ⚠️ 若保單 PDF 有多頁，請先在本機合成一個 PDF 再上傳。

## 具體步驟

### Step 1：重新設計資料結構（state）

- 把現有的全域 `amount / planType / planCode / year` 改為**每個 file 一份設定**
- 每個 file 對應一筆 policy 物件：
  ```
  { file, amountType: "計劃別" | "單位數" | "保額", amountValue: string, prefillDone, result, status }
  ```
- `status` 追蹤每張保單分析進度：`idle | prefilling | analyzing | done | error`

### Step 2：改造上傳區塊 UI

- 每個上傳的 file 渲染成一行：
  ```
  [PDF 圖示 + 檔名（截短）]  [類型 ▼ 計劃別/單位數/保額]  [值輸入框]  [prefill 狀態]  [✕]
  ```
- 上傳後自動觸發 per-file prefill（呼叫現有 `/api/prefill`），偵測到類型自動選取
- 若 prefill 偵測到 planOptions，類型自動設為「計劃別」並顯示下拉

### Step 3：新增「分析全部」按鈕邏輯

- 按下後，依序（或並行 max 3）呼叫現有 `/api/analyze` endpoint
- 每個 file 用自己的 amountType + amountValue 組成 FormData
- 分析過程中，每行右側顯示進度（Spinner → ✓ / ✗）
- 全部完成後顯示結果區

### Step 4：新增合併結果元件 `AggregatedChart`

- 接收多張保單的 result 陣列
- 對相同的 coverage 項目加總（如：所有保單的「住院日額」相加）
- 顯示格式：保障項目 + 各保單分項 + 合計欄
  ```
  項目        國泰人壽  富邦意外  南山醫療  合計
  住院日額     800元     —        500元    1,300元
  ICU 日額    1,600元   —        —        1,600元
  意外身故     —        200萬     —        200萬
  ```
- 此元件放在結果區頂部，下方保留個別保單的 Tab 切換

### Step 5：結果區 Tab UI

- Tab 標題：`[合併總表]  [國泰人壽]  [富邦意外]  [南山醫療]`
- 合併總表：Step 4 的 AggregatedChart
- 個別 Tab：沿用現有 InsuranceChart 元件，傳入該張保單的 result

### Step 6：保留現有單張流程相容性

- 若只上傳一個 file，「分析全部」的行為與原本相同
- 分析完後只顯示單張全險圖（不顯示合併 Tab），視覺不變

## 預計成果

做完以後你會得到：
- 上傳多個保單 PDF → 自動偵測每張的類型與計劃
- 一鍵分析全部 → 逐張顯示進度
- 看到「保戶總保障合計表」（哪個項目加總多少）
- 可切換到個別保單查看詳細全險圖

## 不包含在這次的範圍

- 保戶姓名 / 資料管理（不儲存保戶 profile）
- 保障缺口自動建議（不做 AI 推薦功能）
- 多張圖片組合成一張保單（一個 file = 一張保單，無分組功能）
- 修改 `/api/analyze` 後端（完全複用現有 API）

## 可能遇到的風險

- **InsuranceChart 資料結構不一致**：不同保單 AI 回傳的 JSON 欄位可能不同，合併時需做防禦性處理（欄位不存在就跳過）
- **並行 N 個 API 呼叫**：若保戶有 8 張保單，同時打 8 個 Anthropic API 可能較慢，改為最多同時 3 個（throttle）
- **prefill 誤判類型**：若自動偵測錯誤，UI 讓使用者手動覆寫即可，不影響主流程
