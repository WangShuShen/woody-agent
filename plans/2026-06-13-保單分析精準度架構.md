# 保單分析精準度提升：三層品質架構

> 建立時間：2026-06-13
> 類型：改善優化
> 狀態：待執行

---

## 你要做的事（一句話版）

建立「測試案例庫 → 各險種專科提示詞 → 程式輸出驗證」三層機制，讓保單分析從「AI 猜測」升級成「可驗證、可迭代」的系統。

## 背景和動機

目前分析流程已有雛形（Haiku 分類 → Sonnet 專科分析），但只有「定額醫療」有專科提示詞，其他七種險種靠通用提示詞，導致三種常見錯誤同時存在：
- 金額倍數未換算（填計算式而非結果）
- 欄位歸錯類（如實支誤填進定額）
- 漏填條款中的給付項目

更大的問題是：改完 prompt 不知道有沒有進步，改 A 壞 B 也不會被發現。

---

## 架構設計（三層）

```
保單 PDF
   ↓
[Layer 0] Haiku 分類偵測（現有）
   ↓ category
[Layer 1] 各險種專科提示詞（待補齊）
   ↓ JSON
[Layer 2] 程式驗證規則（待建立）
   ↓ 通過 or 警示
[顯示] InsuranceChart / InsuranceFormChart

測試案例庫 ←──────────────────── 每次修改後跑比對
```

## 第一批：建立測試案例庫

### Step 1：確定測試格式

每個測試案例是一個資料夾，包含：
```
tests/cases/
  定額醫療-南山QDHL2/
    input.pdf          ← 真實條款 PDF
    expected.json      ← 手動標記的正確輸出
    notes.md           ← 特別難分析的點（選填）
  意外險-富邦PA/
    input.pdf
    expected.json
  ...
```

`expected.json` 格式與現有 `/api/analyze` 輸出一致，可直接做 diff 比對。

### Step 2：每個險種選 1-2 張保單建案例

優先順序（依錯誤複雜度排列）：
1. **意外險** ── 骨折附表倍數最複雜，最常出錯
2. **醫療實支** ── 實支 vs 定額容易混淆，且有正/副本差異
3. **防癌險** ── 各等級癌症給付欄位最多
4. **壽險** ── 相對簡單，可快速建立
5. 失能 / 長照 / 重大傷病 / 重特定疾病（通常結構較單純）

### Step 3：建立測試腳本

新增 `scripts/test-analysis.mjs`，讀取 `tests/cases/*/expected.json`，對每個案例呼叫分析 API，然後顯示：
- ✅ 完全一致的欄位數
- ⚠️ 值不同的欄位（顯示期望值 vs 實際值）
- ❌ 遺漏的欄位

**產出**：可在 terminal 執行 `node scripts/test-analysis.mjs` 看比對報告。

### Step 4：依序補寫 lib/specialistPrompts.ts

每個專科提示詞必須包含：
1. **保額來源識別** ── 如何從條款找到基礎金額（附表型 / 直接保額型 / 倍數回推型）
2. **完整術語對照表** ── 該險種所有可能的中文表達 → schema 欄位
3. **換算規則（含範例）** ── 每種倍數/百分比計算寫一個具體範例
4. **強制步驟** ── 「先列出所有給付章節名稱，逐一確認對應欄位」

### Step 5：補完後對測試案例跑比對，確認進步

每個險種做完就跑一次 `test-analysis.mjs`，比較：
- 改前：有幾個欄位正確
- 改後：有幾個欄位正確
- 有沒有改好 A 壞 B

## 第三批：程式輸出驗證規則

### Step 6：建立 lib/validateAnalysis.ts

分析輸出後，對 JSON 做以下程式檢查（不需要 AI，純邏輯）：

**格式規則（高優先）：**
- 金額欄位不能包含 `×`、`%`、`+`、`(` → 代表 AI 沒有換算
- 金額欄位必須以數字開頭（如 `1,000元/日` ✅，`住院日額之2倍` ❌）
- 若 category = 定額醫療，`fixedMedical.hospitalDaily` 不能為空
- 若 category = 意外險，`accident.deathDisability` 不能為空

**合理性規則（中優先）：**
- 住院日額不應超過 50,000（超過可能是計算式沒換算）
- 保額萬元數不應為 0
- annualLimit 不應小於 hospitalDaily × 30

**分類一致性規則（中優先）：**
- category = 定額醫療 時，`medicalReimbursement` 區塊應為空（反之亦然）
- category = 意外險 時，`fixedMedical` 區塊應為空

### Step 7：驗證結果整合進 UI

- 若驗證發現問題 → 在分析結果頂部顯示警示橫幅（黃色），列出問題項目
- 使用者可選擇「忽略」或「重新分析」
- 已有的 `/api/verify` 做 AI 深度稽核，驗證規則做格式快速稽核，兩者互補

## 設計準則摘要（貼到 AGENTS.md 或專案文件）

每次新增/修改分析功能時必須遵守：

1. **每個險種必須有自己的專科提示詞**，禁止靠通用提示詞處理複雜換算
2. **新增案例測試**：修改任何提示詞前，先確認測試案例庫有對應案例
3. **金額欄位零容忍**：任何含有計算式的金額欄位都算 bug，不是警告
4. **倍數一律換算**：條款中出現「×N倍」「N%保額」「額外加給」，最終填入的一律是換算後的實際數字
5. **extras 是安全網**：有條款但找不到對應欄位的，全部進 extras，不能漏
6. **測試回歸**：每次部署前跑一次 test-analysis.mjs，有退步的不能合併

## 預計成果

做完三批之後：
- 每張保單分析完，30 秒內可知道「這次輸出有沒有明顯格式錯誤」
- 修改提示詞時有數字依據（正確欄位從 12/20 提升到 18/20）
- 同事回報「分析怪怪的」時，可以快速定位是哪個步驟的問題

## 不包含在這次的範圍

- 不做 UI 上的手動欄位編輯介面（已有修正欄位功能）
- 不建自動化 CI 測試（手動跑腳本即可）
- 不改變現有的資料庫 schema

## 可能遇到的風險

- **測試案例 PDF 敏感性**：用真實條款 PDF 做測試沒問題，但不要用含個人保戶資料的保單正本
- **expected.json 維護成本**：提示詞改完輸出變了，expected.json 要跟著手動更新，這是設計上的必要成本
- **AI 輸出非確定性**：同一份 PDF 分析兩次可能有小差異，建議測試腳本用「欄位是否非空」而非「完全字串比對」
